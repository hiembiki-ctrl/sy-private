# 계정과 사용자별 저장

## Decisions

- 사용자 계정과 사용자별 데이터 저장은 Supabase 하나로 해결한다. 로그인은 Supabase Auth의 이메일과 비밀번호 방식, 저장소는 Supabase의 Postgres다.
- 사용자별 데이터는 소유자만 읽고 쓸 수 있게 DB 수준에서 막는다. 화면 숨김이나 클라이언트 상태만으로 접근을 통제하지 않는다.
- 도시와 일정 열람처럼 계정이 필요 없는 기능은 로그인과 Supabase 연결 여부에 의존하지 않는다. 계정이 필요한 기능(저장 일정)만 로그인 뒤에 열린다.
- 로그인 방식은 이메일과 비밀번호 하나다. Google OAuth 같은 다른 방식은 준비되면 추가한다.

## Boundaries

- 이 결정은 계정, 로그인, 사용자별 저장에 적용한다. 지구본, 도시 일정 콘텐츠의 출처([itinerary-content-source](itinerary-content-source.md))에는 영향을 주지 않는다.
- 클라이언트에는 공개 가능한 키만 두고, 비밀값은 저장소와 브라우저에 두지 않는다.

## Why

사용자가 DB와 로그인 서비스 선택을 맡기면서 Google OAuth 2.0과 사용자별 일정 저장을 요구했고, 이후 OAuth 설정 없이 먼저 진행하려고 이메일과 비밀번호 로그인으로 바꿨다. Supabase는 Postgres와 두 로그인 방식을 한곳에서 제공하고, 행 단위 보안으로 "내 일정은 나만 본다"를 DB가 보장한다. 이 프로젝트에는 Supabase용 공식 스킬이 설치되어 있어 구현 중 최신 지침을 따를 수 있다. 계정 없이 쓰는 경험이 이 서비스의 가벼움 원칙의 핵심이라 열람은 계정과 분리했다.

## Reconsider when

- 무료 플랜의 비활성 일시정지(7일 미사용 시 자동 정지)가 실제 사용에 문제가 될 때
- Google 등 다른 로그인 수단이 필요해질 때
- 저장 데이터가 사용자별 목록을 넘어 서비스 전체 집계나 공유로 확장될 때

## Still-rejected alternatives

- Firebase 또는 Auth 전용 서비스와 별도 DB 조합 — 서비스가 둘로 나뉘고 사용자별 접근 통제를 DB에서 직접 보장하기 어렵다. Supabase가 요구를 못 채울 때 다시 검토한다.

## Evidence worth preserving

- 무료 플랜(2026-10 검색 기준): Auth 월 5만 명, DB 500MB, 프로젝트 2개, 7일 비활성 시 자동 일시정지. 상시 운영에는 유료 플랜이 필요할 수 있다.
- `@supabase/ssr` 0.12.7은 `@supabase/supabase-js ^2.114.0`만 피어로 요구하고 Next.js 버전 제약은 없다. 이 프로젝트의 Next.js 16에서 실제로 동작하는지는 구현 때 확인해야 한다.
