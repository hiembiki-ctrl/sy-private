# 요청형 여행지 검색

로그인한 사용자가 요청하면 위키 공개 데이터에서 여행지를 모아 여행지 DB에 저장하고, 다음부터는 모든 사용자가 DB에서 읽게 한다.

## Required sources

- [itinerary-content-source](../../decisions/itinerary-content-source.md): 어떤 출처를 쓸 수 있는지, 저장이 허용되는 출처로만 한정한다는 규칙, Google 계열을 쓰지 않는 이유를 정한다.
- [account-and-storage](../../decisions/account-and-storage.md): 로그인 방식과 "열람은 계정이 필요 없다"는 원칙, 비밀값을 클라이언트에 두지 않는다는 규칙을 정한다.
- 용어는 [GLOSSARY.md](../../../GLOSSARY.md)의 지원 도시, 도시 요청, 장소 보강을 따른다.

## Outcomes

1. 로그인한 사용자가 지원 도시에 없는 도시의 이름을 입력해 도시 요청을 하면, 진행 표시를 보며 기다린 뒤 지구본에 새 도시 점이 생기고 그 도시의 일정이 열린다. 새 도시는 모든 사용자에게 보인다.
2. 로그인한 사용자가 이미 있는 도시에서 장소 보강을 요청하면, 진행 표시를 보며 기다린 뒤 새 장소가 그 도시의 일차 코스에 끼워 들어간다. 보강된 장소도 모든 사용자에게 보인다.
3. 한 번 모은 내용은 DB에 저장되어, 다음부터는 요청 없이 DB에서 읽는다. 열람은 로그인 없이 가능하다.
4. 요청으로 들어온 장소에는 출처 문서로 가는 링크가 보이고, 위키백과 글이 CC BY-SA 4.0임을 밝힌다. 직접 작성한 장소에는 링크가 없다.

## Scope

- 포함: 도시 요청, 장소 보강, 진행 표시, 요청 한도, 출처 표시, 요청으로 만든 도시와 장소의 DB 저장.
- 출처는 한국어 위키백과, 위키데이터, 위키보이지의 공개 데이터이다.
- 요청으로 만든 도시도 기존 도시와 똑같이 일수 선택, 4일 이상의 근교 일정, 도시와 일수 저장이 된다.

## Acceptance criteria

- 로그아웃 상태에서는 도시 요청과 장소 보강 버튼이 보이지 않거나 로그인을 안내한다. 도시 열람은 영향받지 않는다.
- 도시 이름을 입력하면 후보 도시 목록이 나오고, 사용자가 하나를 고른 뒤에야 모으기를 시작한다. 이미 지원 도시이면 새로 만들지 않고 그 도시를 연다.
- 요청한 도시는 도시 안 1~3일차(각 일차 장소 1개 이상)와 근교 4곳(각 장소 1개 이상)이 갖춰져야 지원 도시가 된다. 갖춰지지 못하면 지원 도시로 저장하지 않고 이유와 함께 실패를 알린다.
- 진행 중에도 다른 도시는 계속 둘러볼 수 있다. 한도 시간(2분)을 넘기면 실패로 처리하고, 실패해도 DB에는 불완전한 도시가 남지 않는다.
- 같은 도시에 요청이 동시에 들어오면 하나만 처리하고 나머지는 같은 진행 상태를 본다.
- 사용자당 하루 도시 요청 3회, 장소 보강 3회까지 허용하고, 초과하면 이유를 알리고 시작하지 않는다.
- 장소 보강은 이미 있는 장소와 같은 장소를 다시 넣지 않는다. 새 장소를 하나도 못 찾으면 그렇게 알린다.
- 보강된 장소는 좌표가 가장 가까운 일차의 코스 끝에 붙고, 한 일차는 최대 5곳이다. 가까운 일차가 가득 차면 가장 적은 일차에 붙는다. 좌표가 없는 장소는 가장 적은 일차에 붙는다.
- 요청으로 들어온 장소는 출처 문서 링크와 함께 보이고, 같은 문서를 서로 다른 장소에 쓰지 않는다.
- 일반 사용자 권한으로는 도시와 장소를 직접 쓸 수 없고, 쓰기는 서버만 한다.
- 새 도시도 저장 일정에 저장할 수 있다.
- 위키 서비스가 응답하지 않거나 결과가 비어도 기존 도시 열람은 영향받지 않는다.

## Constraints and rationale

- 저장을 허용하는 출처만 쓴다. Google 검색 근거와 Places 내용은 약관상 DB 저장과 공유가 막혀 쓰지 않는다.
- 로그인한 사용자만 요청한다. 요청은 외부 호출 비용과 남용 위험이 있고, 열람과 달리 공용 DB에 쓰기 때문이다.
- 결과는 검수 없이 바로 모두에게 공개한다. 사용자가 요청한 즉시 결과를 보는 것이 이 기능의 가치이고, 대신 출처 링크로 사용자가 직접 확인하게 한다.
- 일정 구조는 바꾸지 않는다. 일차는 3일 도시 안과 4곳 근교이고 일수 선택은 1~7일이다. 보강은 이 구조 안에서 일차 코스를 늘리는 방식이다.
- 기후, 여행하기 좋은 계절, 추천 일수는 위키 공개 데이터에서 신뢰할 수 있게 얻을 수 없다. 요청으로 만든 도시는 이 값이 없으면 도시 정보 줄에서 해당 항목을 생략한다.

## Assumptions

- 도시 요청과 보강 한도는 사용자당 하루 각 3회이고 2분 한도는 첫 구현의 기본값이다. 사용해 보고 조정한다.
- 근교 4곳은 도시 주변에서 한국어 위키백과 문서가 있고 유명한 지명 순으로 고른다.
- 요청으로 만든 장소의 설명은 한국어 위키백과 문서의 첫 문장이다. 한국어 문서가 없는 장소는 쓰지 않는다.
- 도시 이름 후보는 위키데이터에서 도시나 마을로 분류된 항목에서 찾는다.
- 좌표는 위키데이터 값을 쓴다.

## Off-limits

- Google Places, Gemini 검색 근거, Custom Search를 이 기능의 출처로 쓰지 않는다. 약관상 저장과 공유가 허용되지 않기 때문이다.
- 사용자가 요청한 장소를 수정하거나 지우는 화면은 만들지 않는다. 지금은 DB에서 직접 지운다.
- 예약, 결제, 일정 항목 편집, 개인 맞춤 추천은 다루지 않는다.

## Deferred

- 잘못되었거나 부적절한 장소를 사용자가 신고하는 흐름과 관리자의 삭제·검수 화면. 그전까지 공개 즉시 반영의 위험은 관리자가 DB에서 직접 지워서 막는다.
- 기후, 좋은 계절, 추천 일수를 요청으로 만든 도시에 채우는 방법.
- 도시가 수백 곳으로 늘 때 지구본 점과 도시 목록을 어떻게 덜 복잡하게 보여 줄지.

## Remaining risks

- 위키 공개 데이터는 소도시의 근교와 장소가 비는 경우가 흔하다(2026-10 이 프로젝트 실험). 요청한 도시의 상당수가 "갖춰지지 못해" 실패할 수 있다. 실패율이 높으면 출처 선택을 다시 정한다.
- 검수 없이 공개되므로 위키백과 첫 문장이 여행 정보로 어색하거나 부정확한 항목이 섞일 수 있다.
- PRODUCT.md는 "주요 도시만 클릭 가능"이고 "도시를 클릭했을 때만 일정을 만든다"고 적고 있어, 사용자 요청으로 도시가 늘어나는 이 기능과 어긋난다. 구현 전후에 `define-product`로 제품 정의를 갱신해야 한다.
- 위키 API 정책(요청 속도, User-Agent)과 서비스 안정성에 기능이 의존한다.
- 요청 한도를 사용자 계정 기준으로 세므로, 계정을 여러 개 만들면 우회할 수 있다.
